# Create

`${CLAUDE_SKILL_DIR}` is the folder that holds this SKILL.md and `references/` (the engine is in `../engine`); engine commands, document paths and clients that leave the variable as is: "Paths" in `SKILL.md`.

Scenes the router sent to the simple path (the analyze step, "Simple path") don't come here.

## Time limits - hard

Per illustration: scenario - 3 minutes, animation - 7 minutes, one look at the frame sheets - 2 minutes: it is advice, nothing is rebuilt on its remarks, fixes of script findings - 4 minutes. For scenes with people (a character, a hand, a group of people): animation - 15 minutes, fixes of script findings - 12 minutes; the rest as above. Note the time at the start of a stage (`node -e "console.log(Date.now())"`, milliseconds: works in every shell, PowerShell included) and check it before every new round. Time is up - stop and deliver the best build so far; no extensions and no extra attempts. The deadline goes into the prompt of every subagent (animator, fixer).

Write the minutes of each stage, the cost of the scene and the outcome to `<style folder>/out/<scene>.timing.json`: `{"scenario_min": 2.5, "animation_min": 11, "judge_min": 2, "fixes_min": 6, "cost_usd": 4.2, "fix_rounds": 1, "stop_reason": "passed", "tried": "a longer swing"}` (`stop_reason`: `passed`, `limit` or `engine`; leave out what is unknown; optional `composition`: `character`, `hand`, `group` or `object`). `make.js` adds its own `builds`, `build_min` and `engine_stop` on every run (batch too) and keeps the keys you wrote. Do not write `first_try` - it is the user's word (`clean`: his first look took the scene without edits, `edited`: after them), set by `ledger.js rate`. The run ledger reads this file.

Input: a style folder with `scenes/*.json`. If the analyze step stopped on warnings ("stop, we won't cope"), this skill is run only after the person said go. The `no-stop` mode is passed on to verify.

1. **Setup.** Run `node "${CLAUDE_SKILL_DIR}/../engine/bin/setup.js"` only when `~/.animator/tools.json` is missing or broken (it is not needed on every run) - safe to re-run, it installs nothing by itself. Exit code 0, "Setup done" - go on. Code 2 - it printed a plan and changed nothing: show the plan to the user and, only once they agree, run it again with `--yes`. Code 3 - no ffmpeg with the needed encoders: give the user the install command it printed and stop (they install ffmpeg themselves). Any other failure - tell the user the reason in one line and stop.
2. **Building in portions.** When the task names scenes (one scene, or a folder shared with other runs), build only those: `node "${CLAUDE_SKILL_DIR}/../engine/bin/make.js" <style folder>/scenes/<name>.json` for each, never `batch.js` over the whole folder. For a whole style folder, repeat `node "${CLAUDE_SKILL_DIR}/../engine/bin/batch.js" <style folder> --limit 20 --jobs 3` until `remaining` in the final line is 0. Each call is up to 20 scenes, 3 at a time, and fits in a few minutes (20 scenes × ~18 s / 3 threads ≈ 2 minutes; a Bash call lives no longer than 10 minutes, so don't increase the portions). The result of each call is one line per scene and the JSON `{"done":…,"failed":…,"error":…,"skipped":…,"remaining":…,"tried":…}`. `tried` - scenes with status failed/error that were already tried and haven't changed since: they aren't rebuilt and aren't counted in `remaining`; verify will deal with them. Don't fix scenes with status failed/error - that is verify's job. A re-run continues from where it stopped: finished and unchanged scenes are skipped, a scene that another run is building right now waits. If `remaining` doesn't decrease for two calls in a row - the scenes are stuck in another run: wait 10 minutes and repeat.
3. **Mac.** If this is macOS - `node "${CLAUDE_SKILL_DIR}/../engine/bin/mp4.js" <style folder>/out` finishes the MP4 for scenes built on Windows. If `mp4.js` fails - tell the user in one line on which scene, and continue to verify.
4. **Then without stopping** - run the verify step on this style folder (in the same mode).

Ask nothing. Don't edit scenes: fixing is verify's job.

The status of a build may carry `lineend` / `lineover` warnings (the end of a line came off the lines it stopped at, lines of two parts meet anew) and `make.js` stops a cut whose line shows in motion (`hair`): the warnings are places to look at, not faults - verify cuts them out as `places.png` for the judge; do not edit the scene on them here.

Loop is continuous: a scene's tracks follow the plan's `Loop:` line - one length, periods that divide it. Cyclic and background tracks pass the seam in motion (a sine with a phase, the `through` curve), never an ease to a stop; the whole frame must not rest at the seam, and the loop length is a common multiple of the periods (`common.md` "The loop is continuous"). Pose on frame 0 = the SVG drawing; that does not mean zero speed.

Default output is Lottie JSON and MP4. The deadline for an animation is 7 minutes (15 for scenes with people). One animation, one file: every animation is saved and handed over as its own file (and its own dashboard card) - never a side-by-side or paired clip. When two builds of one scene are compared, each goes in its own file; the lengths may differ, no need to equalize them: what matters is that each file is a clean loop on its own, and the MP4 is never cut mid-cycle (leave the Lottie as built).
